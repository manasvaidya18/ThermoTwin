Rules that shape every decision
  • AI tools, APIs and open source are allowed. Every member must be able to explain every component, so keep a log of what you used and why.
  • Pre-built work is allowed. Whatever you build tonight counts.
  • Judging weights are not published. The handbook's demo story is the best guide: Problem, Approach, Proof, Engineering, Impact.
  • Use public, sample or synthetic data only, use your own API keys, never commit keys, credit everything you reuse. The DeltaV sample data is for hackathon use only and must not be shared.

How to work as a team of four

Roles

  • Algorithm or ML lead owns the core engine and the benchmark numbers.
  • Data and simulation engineer owns the generator, test sets and the planted-fault suites.
  • Product and frontend lead owns screens, the demo flow and the report visuals.
  • Integration and pitch lead owns the API, packaging, the PPT, the recorded demo and the viva preparation. Everyone else rotates into this role for the last six hours.

Rhythm

  • Two vertical slices first (input to output, ugly), then deepen. Never build modules in isolation for more than half a day.
  • One shared repository with a main branch that always runs. A make demo or run_demo.py command that produces the demo from sample inputs.
  • A decision log file: every model, library and AI tool used, with one line on why. The handbook says you will be asked.
  • Freeze features 6 hours before every deadline and spend the time on reliability and rehearsal.

Definition of done for each stage

  • Round 1: PPT plus one real chart or screenshot from a running prototype.
  • Round 2: someone outside the team can run it from a README in under 10 minutes; a 3-minute recorded demo exists.
  • Finale: the demo works offline from local files; a backup video and sample inputs sit on the laptop.

Viva readiness

  • Each person can explain the whole pipeline in one minute and their own module in five.
  • Each person can state two limitations and what you did about them.
  • Every number on a slide can be reproduced by a command.

Seven patterns that apply to every problem

  1. Evidence on every output. The packs keep asking for proof: cited code, linked evidence, expected versus found, a reason code, a TQ with a reason. Treat "show your work" as a core feature.
  2. Abstain rather than bluff. A verify lane, an "I could not ground this" answer, a low-confidence flag. Judges forgive honest gaps and punish confident errors.
  3. Declarative over hard-coded. Rules in YAML, checks as plug-ins, hardware as a profile. Hidden tests reward this because new inputs need no code change.
  4. Build your own benchmark. Planted bugs, planted lies, planted faults, synthetic hidden splits. One chart of measured results beats three slides of claims.
  5. Facts by code, judgement by LLM, evidence by pointer. Anything computable or checkable is done deterministically. The model only interprets, and every sentence it writes must point at evidence that code can verify.
  6. Fairness and limits as visible features. State assumptions, failure modes and what you did about them. Track 4 scores this explicitly.
  7. Demo discipline. A rehearsed 5-minute flow, a recorded backup, local sample inputs and a 30-second explanation before the deep dive.
