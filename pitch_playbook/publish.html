How to work as a team of four

Roles

  • Algorithm or ML lead owns the core engine and the benchmark numbers.
  • Data and simulation engineer owns the generator, test sets and the planted-fault suites.
  • Product and frontend lead owns screens, the demo flow and the report visuals.
  • Integration and pitch lead owns the API, packaging, the PPT, the recorded demo and the viva preparation. Everyone else rotates into this role for the last six hours.

Rhythm

  • Two vertical slices first (input to output, ugly), then deepen. Never build modules in isolation for more than half a day.
  • One shared repository with a main branch that always runs. A make demo or run_demo.py command that produces the demo from sample inputs.
  • A decision log file: every model, library and AI tool used, with one line on why. The handbook says you will be asked.
  • Freeze features 6 hours before every deadline and spend the time on reliability and rehearsal.

Definition of done for each stage

  • Round 1: PPT plus one real chart or screenshot from a running prototype.
  • Round 2: someone outside the team can run it from a README in under 10 minutes; a 3-minute recorded demo exists.
  • Finale: the demo works offline from local files; a backup video and sample inputs sit on the laptop.

Viva readiness

  • Each person can explain the whole pipeline in one minute and their own module in five.
  • Each person can state two limitations and what you did about them.
  • Every number on a slide can be reproduced by a command.

Seven patterns that apply to every problem

  1. Evidence on every output. The packs keep asking for proof: cited code, linked evidence, expected versus found, a reason code, a TQ with a reason. Treat "show your work" as a core feature.
  2. Abstain rather than bluff. A verify lane, an "I could not ground this" answer, a low-confidence flag. Judges forgive honest gaps and punish confident errors.
  3. Declarative over hard-coded. Rules in YAML, checks as plug-ins, hardware as a profile. Hidden tests reward this because new inputs need no code change.
  4. Build your own benchmark. Planted bugs, planted lies, planted faults, synthetic hidden splits. One chart of measured results beats three slides of claims.
  5. Facts by code, judgement by LLM, evidence by pointer. Anything computable or checkable is done deterministically. The model only interprets, and every sentence it writes must point at evidence that code can verify.
  6. Fairness and limits as visible features. State assumptions, failure modes and what you did about them. Track 4 scores this explicitly.
  7. Demo discipline. A rehearsed 5-minute flow, a recorded backup, local sample inputs and a 30-second explanation before the deep dive.

Understand the problem

In plain words

Vaccines, insulin, blood products and some foods must stay inside a temperature band. Vaccines are usually kept at 2 to 8 °C. Today's monitoring is a thermometer with a threshold: it sounds the alarm once the limit is already crossed, so the stock is already at risk. The task is to look at the sensor history and predict, minutes ahead, that a breach is coming, so a person can move the stock or fix the fridge in time. The prediction must also be trusted. A system that cries wolf gets ignored, so the PDF repeatedly says "keep false alarms under control".

PDF error to be aware of

In the Track 4 PDF, the "Problem Statement" box under the cold-storage title contains the indoor-positioning paragraph by mistake. The real task is the bullet list on the next page. Mention the real task in your slides and ask the organisers to confirm.

What the PDF requires

  • Analyse temperature and related time series; identify gradual degradation, abnormal rate of change and sudden failure patterns.
  • Predict the probability of an excursion within a defined future window.
  • Tell normal recovery (for example after a door opening) apart from conditions that need intervention.
  • Name likely contributing factors (door events, ambient change, loss of cooling effectiveness) where those fields exist.
  • Give explainable warnings with a confidence or risk level, and a simple dashboard or API with current state, prediction and reason.
  • Data fields suggested: timestamp, storage temperature, ambient temperature, door state, cooling state, rate of change, sensor noise, event or failure labels. Scenarios: normal operation, door opening, slow cooling degradation, sudden cooling failure, sensor spikes, recovery. A hidden synthetic set with unseen combinations of faults and noise is used for scoring.
  • Scoring dimensions (common to Track 4): hidden-test performance, robustness to noise, missing data and unseen conditions, explainability, deployability as API, app or edge component, visualisation and demo, clarity of assumptions, limitations and validation.

Our concept: ThermoTwin

Instead of one anomaly detector, build a small digital twin of each fridge that learns the unit's own physics, then forecast from how the unit deviates from its healthy self. Three ideas carry the pitch.

1. The twin sees what a threshold cannot

Each unit's cooling strength and insulation are estimated online. After a door closes, a healthy unit follows a known recovery curve. A failing one does not. The residual between the two is the strongest early signal and is physically explainable.

2. The Spoilage Clock

An alert says "7.4 °C" but a 6 minute blip and a 3 hour excursion are not the same harm. We track cumulative heat exposure with the Arrhenius weighting behind MKT and vaccine vial monitors, so severity scales with real damage.

3. Alerts with a false-alarm budget

The alert threshold is not a guess. It is chosen to hit a stated budget (for example one false alarm per unit per month) and shown live against a classic threshold alarm on the same data.

Why we win

Every judging dimension has a visible answer: hidden-test performance (leave-one-fault-out numbers), robustness (noise and missing-data grid), explainability (reason codes), deployability (API plus edge model), demo (fleet dashboard with what-if), validation clarity (stated assumptions). Why we might lose

Many ML teams will pick this track, so a plain "XGBoost plus dashboard" would not stand out. The twin, the Spoilage Clock and the alert-budget curve are what separate us. Realism of the simulator will be questioned, so document assumptions openly.

How it works inside

1. The simulator

A two-node thermal model: one node for the air where the sensor sits, one for the stored product. A thermostat with hysteresis drives the compressor. Parameters are randomised per unit so no two fridges are identical.

Air node      C_a * dT_a/dt = UA*(T_amb - T_a) - Q_c*s(t) - h_p*(T_a - T_p) + Q_door(t) + Q_defrost(t)
Product node  C_p * dT_p/dt = h_p*(T_a - T_p)
Thermostat    s(t)=1 when T_a > T_hi ; s(t)=0 when T_a < T_lo        (hysteresis)
Door          Q_door = k_door * (T_amb - T_a) * 1[door open]
Degradation   Q_c(t) = Q_c0 * (1 - d(t)),  d ramps over days   |   leak: UA(t) = UA0 * (1 + e(t))
Sudden fail   Q_c -> 0 at t_f   |   Power cut: s(t)=0 and fans off for a window
Sensor        y = T_a + bias + noise;  spikes w.p. p_s;  dropout w.p. p_d;  stuck-at episodes

Use one reading per minute. Calibrate the constants so a closed healthy unit saw-tooths between about 3 and 5.5 °C, warms 0.5 to 1.5 °C in ten minutes with the compressor off, and recovers about 1 to 2 °C within 5 to 10 minutes of a short door opening. 3. The twin: learning each unit's physics online

During compressor-off windows the air warms toward ambient: dT/dt ≈ (UA / C_a) (T_amb minus T). A regression of the observed slope on (T_amb minus T) gives the leakage index. During compressor-on windows the cooling rate is dT/dt ≈ minus (Q_c / C_a) plus the leak term, so a regression gives the cooling health index, normalised by the unit's own first-week baseline (1.0 means healthy). Use recursive least squares with a forgetting factor so the estimate tracks change but is stable. After each door close, replay the healthy model from the pre-opening state and compare predicted and actual recovery. The ratio becomes the recovery ratio feature. A door-open recovery gives a ratio near 1; a failing compressor gives a ratio that keeps growing.

4. Forecaster and time to breach

  • One LightGBM binary classifier per horizon (15, 30, 60). Train on episodes, never on shuffled rows. Class weights or focal-style weighting for the rare positives.
  • Probability calibration with isotonic regression on the validation episodes so "0.8" means about 80%. Report reliability curves and expected calibration error.
  • Time to breach: LightGBM quantile regression (10th, 50th, 90th percentile) on the positives. This gives the countdown with a confidence range, for example "34 min (18 to 61)".
  • Baselines to show: threshold alarm, rate-of-change rule, isolation forest, and a small TCN or GRU. The point is that the hybrid wins on lead time at equal false-alarm rate and on unseen fault combinations.

6. Alert policy

  • Levels: Watch (p30 at least 0.3), Warning (p30 at least 0.6 or median time to breach at most 45 min), Critical (p15 at least 0.7 or breach in progress).
  • Stability rules: require 3 consecutive evaluations above the level (persistence), a 30 minute cooldown per unit and level, and auto-clear with hysteresis.
  • Threshold search: pick the thresholds that maximise recall subject to the stated false-alarm budget on validation episodes, or minimise expected cost = C_miss × misses + C_alert × false alarms. Publish the budget and the resulting operating point.
  • Sensor gate: if sensor trust is below its threshold, downgrade to "verify sensor" instead of a product-risk alert.

7. The Spoilage Clock

Each minute at temperature T consumes stability budget in proportion to an Arrhenius factor relative to a 5 °C reference: factor = exp( (ΔH/R) × (1/T_ref minus 1/T) ), with ΔH/R of about 10,000 K, the standard value used in mean kinetic temperature calculations. Illustrative values: 8 °C costs about 1.5 minutes of budget per minute, 25 °C about 11, 40 °C about 56. Integrate over time and compare with a configurable allowance (for example the equivalent of 2 hours at 25 °C). Show a progress bar and a clear label: this is a planning proxy built on a standard assumption, not a regulatory decision rule. Real go or no-go decisions use the manufacturer's stability data and vial monitors.

8. Sensor-trust pre-filter

Before forecasting, run cheap forensic checks (Hampel filter for spikes, flatline run length, variance ratio, gaps). If a spike has no physical story (the compressor state, door and ambient do not explain it), mark the sample untrusted and carry forward the twin's predicted value. This borrows the best idea from T4-3 and is a visible differentiator. Details of the full version are on the SensorCourt page.

9. Edge and API

The forecaster is a small tree ensemble and the twin is a few regressions, so the whole pipeline runs on a Raspberry Pi class device. Export the trees with ONNX or keep LightGBM's native model; report model size and per-prediction latency as the deployability evidence the PDF asks for.

Understand the problem

In plain words

Some fixed devices at known positions (beacons, also called anchors) measure how far away a moving tag is, using ultra-wideband radio time of flight or Bluetooth signal strength. From a few distances you compute the tag's X and Y position. In a perfect room with many beacons this is school geometry. In a real hospital the readings are noisy, some beacons drop out for a while, and walls make the signal arrive late (non-line-of-sight, NLOS), so the measured distance is longer than the true one. The task: estimate position anyway, with fewer beacons than ideal, and report how confident you are.

PDF error to be aware of

The "Suggested Technology" line under this problem (time-series forecasting, anomaly detection, classification, explainable AI) is a copy from the cold-storage problem. For this problem think robust estimation, filtering and sensor fusion. Say so on your slide so the judges see you noticed.

What the PDF requires

  • Estimate target X and Y from range and/or signal-strength measurements, using a reduced number of reference points.
  • Handle noise, missing reference points and intermittent loss; identify or reduce the influence of probable NLOS or biased measurements.
  • Use motion history or temporal filtering where useful.
  • Report position with confidence or uncertainty.
  • Compare accuracy under different infrastructure densities and noise conditions.
  • Dataset suggestion: a virtual room, hospital floor or warehouse with known reference coordinates and simulated trajectories; ideal distance and RSSI plus injected noise, packet loss, NLOS bias and missing anchors; ground-truth coordinates. Hidden test with different paths, noise levels and obstruction patterns.
  • Goal: lowest practical error on the unseen test set.

Our concept: LocusNet

1. Anchor-agnostic learning

The model reads a set of anchor tokens (position, range, signal strength, valid flag), so it accepts any number or placement of anchors. Random anchor dropout during training means the hidden test's different layout is just another draw.

2. Learned trust inside a classical filter

A small model scores each anchor's chance of being NLOS and its bias, and those scores set the noise terms of a Kalman or particle filter with a wall-aware map. We keep the guarantees of filtering and add what learning is good at.

3. Honest uncertainty and a placement advisor

Every fix comes with a calibrated 90% ellipse. The same maths tells a facility where a fourth or fifth beacon helps most, which is the PDF's "reduce installation complexity" in one feature.

How it works inside

1. Simulator

  • Floor plan. A polygon with wall segments (rooms and corridors of a ward, around 30 m by 20 m). A walkable area is stored as polygons so we can constrain particles and classify zones.
  • Trajectories. Pick random waypoints, route along corridors (shortest path on a walkable graph), speed 0.5 to 1.5 m/s with pauses and turns, sampled 5 to 10 Hz.
  • Ranges. r_i = distance(target, anchor_i) + noise + NLOS bias. Noise standard deviation grows slowly with distance. NLOS is decided geometrically (the segment target to anchor crosses a wall) plus random blockage bursts for people and furniture. Bias is positive, exponential or log-normal, larger with more walls crossed.
  • RSSI. Log-distance path loss with per-wall attenuation (a few dB each) and shadow fading, quantised like a real radio.
  • Loss. Bursty packet loss (two-state Gilbert-Elliott chain) plus whole-anchor outages for several seconds.
  • Output table. trajectory id, time, ground-truth x and y, one row per anchor with anchor id and coordinates, range, RSSI, valid flag. Keep the LOS flag in a separate file for analysis only, never as a model input.
  • Hidden split. Different floor layouts, anchor counts and placements, noise levels, NLOS rates and trajectory styles.

3. Robust estimation

  • Weighted least squares. Minimise the sum over anchors of w_i (r_i minus ||x minus a_i||)². Weights from the trust model: w_i = (1 minus P_nlos) divided by sigma_i². Gauss-Newton from a coarse grid initialisation to avoid local minima.
  • Robust loss. Replace the square with a Huber or Cauchy loss so one bad range cannot dominate.
  • Subset consensus (RANSAC style). With K anchors, solve on every subset of size 3 (K is small, so enumeration is cheap), count anchors consistent within a gate, keep the best consensus, refit on its inliers.
  • Two anchors left. Two candidate points. Use the previous position, velocity and the walkable-area map to pick one, and inflate the covariance.
  • One anchor left. Dead reckoning from the motion model; the ellipse grows with time. State this honestly in the UI.

The particle filter is the answer to the two-anchor mirror ambiguity: both candidates survive as clusters until motion and walls eliminate one.

5. The learned model

  • Input. A set of anchor tokens [ax, ay, r, rssi, valid, implied range, residual] plus the previous estimate. Anchors are unordered, so use attention without positional encodings.
  • Output. A position correction relative to the robust estimate (residual learning is more stable than predicting from scratch) and a covariance through a heteroscedastic Gaussian likelihood (predict log standard deviations and a correlation).
  • Training tricks. Random anchor dropout (0 to 60%), random NLOS rate, noise scale, wall layouts and anchor placements for domain randomisation; curriculum from easy to hard.
  • Temporal part. A small GRU over successive corrected estimates as a smoother.
  • Comparison. Report three systems: classical only, hybrid (learned trust plus filter), end-to-end network. Pick the best on validation; show all in the ablation.

6. Calibrated uncertainty

Compute the Mahalanobis distance of the true error under each predicted covariance on a calibration set. Take the 90th percentile of those scores as a scale factor, so the final ellipse is the predicted ellipse multiplied by that factor. On the test set, report coverage per condition (target 90%). When trace(Sigma) exceeds a threshold, return a zone ("probably Ward B, 78%") by integrating the posterior over room polygons instead of a misleading point.

The central idea

A real event moves related sensors together, with plausible delay. A fault is local. So the question for each deviation is not "is this weird?" but "do the other sensors agree?"

Our concept: SensorCourt

Treat each suspicious reading as a case. Four independent witnesses give evidence, a judge combines it into a verdict with a confidence, and a court record shows the reasoning to the operator.

1. Events live in the pattern, faults break it

A PCA model of healthy multi-sensor behaviour splits any deviation in two. The part that stays inside the usual correlation pattern (Hotelling's T²) is a genuine event. The part that breaks the pattern (the Q statistic or SPE) is a fault. Contribution plots name the guilty sensor.

2. Trust is a probability over time

Each sensor has a hidden health state (healthy, drifting, stuck, noisy, spiky, dropout, failed) tracked by an HMM. The trust score is the probability it is healthy, with maintenance forecasts from the drift rate.

3. Keep the lights on

A quarantined sensor is replaced by a virtual sensor reconstructed from its neighbours, so monitoring continues and the operator knows which values are measured and which are estimated.

How it works inside

1. Simulator

  • Latent field. N sensors (8 to 20) at positions p_i. True value x_i(t) = shared diurnal trend + spatially correlated component (a Gaussian process over positions or an AR(1) field with distance decay) + local variation.
  • Genuine events. A plume or pulse starting at a source, reaching sensor i after a delay proportional to distance divided by propagation speed, with amplitude decaying with distance. Also slow ramps (weather fronts).
  • Measurement model. y_i(t) = g_i × (x_i(t) + b_i(t)) + noise_i(t), then faults modify g_i, b_i, noise, or replace the reading.
  • Fault injectors. Offset step, linear drift, gain error, spike train (probability p per sample, random magnitude), stuck-at (hold the last value), noise burst (multiply sigma), dropout (NaN or zero), degradation (slow drift plus rising noise plus response lag).
  • Labels. Per sensor and time: fault type and severity; globally: genuine event active. Training uses single faults; the test set adds two or three simultaneous faults, new severities and event patterns.

3. The T² and Q split in detail

Fit PCA on healthy windows of all sensors (rows = time, columns = sensors, standardised); keep k components covering ~95% variance
For a new sample x:   t = P^T x            (scores)         x_hat = P t        (reconstruction)
   T2 = sum_j  t_j^2 / lambda_j            large  => variation along normal correlated directions    => GENUINE EVENT
   Q  = || x - x_hat ||^2                  large  => variation that breaks the correlation pattern   => SENSOR FAULT
Locate: contribution of sensor i to Q = (x_i - x_hat_i)^2        (largest = guilty sensor)
Iterate: remove (reconstruct) the guilty sensor and re-test; stop when Q is within its control limit
Limits: from percentiles of training T2 and Q or the usual chi-square and weighted-chi-square approximations

Pitch line: events live in the subspace, faults live in the residual. Add the lag-aware check so that real events arriving at neighbours with delay are not mistaken for faults.

4. Fault classifier

A LightGBM multi-class model takes the concatenated witness features and predicts {healthy, spike, stuck, noise, offset, gain, drift, dropout, degradation}. Calibrate with isotonic regression. Show an ablation: forensic only, forensic plus peer, all four. The rules from the witnesses keep it interpretable; the model adds accuracy on mixtures.

5. The judge: HMM trust and alarm verdicts

  • States. H (healthy), D (drifting), St (stuck), N (noisy), Sp (spiky), Dr (dropout), F (failed). Sticky transitions: P(H to H) about 0.999, faults persist.
  • Emission. Calibrated classifier probabilities divided by class priors, fed to the forward algorithm. Posterior at each time gives trust = 1 minus P(any fault state).
  • Health ladder. Trusted (0.9 and up), Watch (0.6 to 0.9), Suspect (0.3 to 0.6), Quarantine (below 0.3), with hysteresis so it does not flicker.
  • Alarm adjudication. When a monitored value crosses its alarm limit, combine: peer corroboration (how many neighbours show the expected signature with the expected lag), sensor trust, and fault-type evidence. Output one of Trusted event, Suspected sensor fault (type, confidence), or Verify. In log-odds form: posterior odds = prior odds × LR(peers) × LR(trust).

6. Repair and planning

  • Virtual sensor. Estimate x̂_i from peers (ridge, PCA reconstruction or GP). Flag the output as "estimated" and keep running alarm logic on it.
  • Drift estimation. Robust regression of y_i on its peer reconstruction over healthy-peer windows gives offset b̂_i and gain ĝ_i. Suggest correction values for recalibration.
  • Maintenance forecast. Fit the trend of b̂_i(t); predict when it will cross the tolerance: "recalibrate within 9 days (6 to 14)". Replace versus recalibrate heuristic: if noise and lag have also degraded, replace.

7. Honest limits

  • Common-mode faults. If every sensor drifts the same way (shared contamination, a bad batch) peer comparison cannot see it. Mitigate with physical bounds, a periodic reference reading, and mixed sensor types.
  • Slow real change versus slow drift. Ambiguous in isolation; peers and physical plausibility help, and the system should say "uncertain".
  • Single sensor. Only forensic and physics witnesses exist, so verdicts are weaker. The UI says so.

Likely judge questions

How is this different from standard anomaly detection?

Anomaly detection says something is unusual. We decide whether the world or the sensor changed, name the fault, track trust over time, and repair the data stream.

What if all sensors fail the same way?

That is a common-mode fault and peer comparison cannot see it. We mention it as a limit and mitigate with physical bounds, reference checks and mixed sensor types.

Will it classify a real event as a fault?

That is the sensitivity side of the triage curve. We tune for 95% genuine-event recall and report what fraction of false alarms are removed at that point.

How does it generalise to unseen fault combinations?

Witness features are fault-agnostic and we train on single faults but test on combinations and new severities, reporting the drop.

Why PCA instead of a deep autoencoder?

PCA gives interpretable T² and Q statistics and contribution plots. We can compare against an autoencoder baseline, but explanation matters here.

Is the virtual sensor safe to use?

It is always labelled estimated, carries an uncertainty, and is used only to keep monitoring alive while a human is notified.

How would this be deployed?

As an API or edge component that sits between the sensor gateway and the alarm system, with a dashboard for maintenance teams.

Understand the problem

The plant, in 60 seconds

A process plant (chemicals, oil and gas, pharma) has thousands of field instruments: pressure and level transmitters, switches, valves, motors. Each instrument sends or receives one electrical signal over a pair of wires. Wires are bundled into multi-pair cables of 24, 12, 6 or 2 pairs and run to a marshalling cabinet in the control room. Inside the cabinet the control system (here Emerson's DeltaV) needs every signal landed on a specific module, called a CHARM, which sits in a slot on a baseplate. Baseplates hang off a CIOC (a controller card), and CIOCs are mounted in a cabinet. Choosing where each signal goes is called IO allocation. Today engineers do it by hand in Excel for 10,000+ signals, and every customer revision means redoing and re-tracing it.

Hardware hierarchy

1 signal = 1 CHARM slot.
12 CHARMs per baseplate.
8 baseplates per CIOC.
4 CIOCs per cabinet.
384 slots per cabinet.

Cables

24, 12, 6 or 2 pairs. A 24-pair fills exactly two baseplates: 22 signals plus 2 wired spare pairs. All pairs of a cable sit side by side in pair order.

Why it is hard

Groups must stay together, A and B must be apart, spares must be left, naming must follow patterns, and the customer will send Rev B next week.

Our concept: Sudoku Engine

1. Rules are data, not code

A small declarative rule language compiles into solver constraints. New rule or new hardware profile means a YAML edit and, for a new rule type, a plug-in class. This directly meets "a new rule or new IO MDB needs no code change".

2. A solver places, a referee proves

Allocation uses constraint programming (OR-Tools CP-SAT). Then an independent referee, written separately, re-reads the output Excel and re-checks every enabled rule. "Zero violations" becomes a certificate you can show.

3. Revisions that barely move anything

Unchanged signals are pinned. Added signals first use wired spare pairs and free slots nearby, then grow outward. The impact report shows the ripple radius and moved signals with reasons.

4. TQs written like an engineer

Every issue the tool cannot resolve becomes a TQ with the rule, the evidence cells, a plain reason and a ready-to-send question. Similar TQs are grouped.

5. AI where it helps

An LLM maps columns, turns plain-English requests into validated rules, drafts TQ wording and mines rules from legacy allocations. It never decides a placement.

6. A board you can read

The Sudoku board shows cabinet, CIOC, baseplate and slot, coloured by group, striped by A/B, with violations pulsing red. Rule playground sliders show cost in cabinets live.

4. The solver, step by step

  1. Normalise. Resolve cables to blocks; compute each block's slot size including spare pairs; handle cables with signals from several groups (flag).
  2. Build kits. Pack small blocks (6 and 2 pairs) of the same lane onto baseplates by first-fit-decreasing; 12-pair is one kit; 24-pair is a double kit with adjacency. A kit is the unit of placement. Record free slots inside each kit (for later spare use).
  3. Warm start. Order groups by file order, lay lanes into CIOCs with next-fit while respecting A/B apart and cabinet reserve. This yields a valid, if not tight, allocation in seconds and serves as the solver hint.
  4. Level 1 model (CIOC and cabinet assignment).
Variables   x[k,m] in {0,1}     kit k placed in CIOC m          (m = 1..M, M from the warm start plus slack)
            y[lane,m] in {0,1}  lane has at least one kit in CIOC m
            z[g,j] in {0,1}     group g has at least one kit in cabinet j  (CIOC m belongs to cabinet ceil(m/4))
            u[j] in {0,1}       cabinet j used
Hard        sum_m x[k,m] = 1                                   (every kit placed once)
            sum_k size_k * x[k,m] <= 8                         (baseplates per CIOC)
            sum_{m in cabinet j} sum_k size_k * x[k,m] <= U    (spare reserve: U = floor((1 - spare_pct) * 32))
            y[lane,m] >= x[k,m]  for k in lane
            y[(g,A),m] + y[(g,B),m] <= 1                       (A and B apart)        [scope parameter: same group or global]
            u[j] >= x-based usage ;  CIOC m used only if m-1 used (symmetry breaking)
Objective   minimise  W1*sum_j u[j]  +  W2*sum z[g,j]  +  W3*sum y[lane,m]  +  W4*(span of each lane's CIOC indices)
            lexicographic weights: W1 >> W2 >> W3 >> W4 ; revision runs add  W0*moves  with W0 largest
  1. Scaling. About 10,000 signals is roughly 900 kits and 110 CIOCs, a manageable model. For larger inputs decompose by group clusters in windows (for example 120 kits), fix the rest from the warm start, solve, and repeat (large neighbourhood search). Use a time limit with the best solution so far, log the bound.
  2. Level 2 (placement inside each CIOC). Sequence kits in lane and cable order, assign baseplate positions 1..8 contiguous; double kits take adjacent positions; inside a baseplate assign slots in order so pairs run consecutively and pair order is kept. Empty baseplates fall to the end of each CIOC and cabinet, which realises the reserve.
  3. Level 3 (names and hardware). Apply the mapping and naming rules; counters per scope; zero-padding from the patterns.

Lower bound for the headline claim. Slots needed = sum of block sizes (spares included). Baseplates needed at least ceil(slots / 12). Cabinets at least ceil(baseplates / floor(32 × (1 minus spare))). Example: 10,000 signals at 92% pair fill is about 10,900 slots, about 906 baseplates, and with 10% spare (28 usable per cabinet) at least 33 cabinets. Report "ours: N cabinets, bound: M, gap: N minus M".

5. Naming engine

Tokens come from project parameters, tag parsing (regular expression on the tag for unit) and counters. Counters are scoped (per area and unit). Support padding and formatting ({seq:04d}). Test with the PDF's examples: AR1-DCS-100-01, AR1CTL10001, AR1-DCM-100-01, AR1CIOC100001, 001-CBP-1. Patterns are validated so unknown tokens are rejected in the panel.

6. The referee

  • Reads only the exported workbook. Rebuilds the hierarchy from cell values, never from solver memory.
  • Checks every enabled rule's check(), plus global invariants: every input signal appears exactly once or has a TQ; no slot used twice; slot indices within capacity; names match patterns; CHARM and terminal block match the mapping.
  • Outputs a violations table (rule, entity, expected, found) and a certificate page: counts checked, violations found, rule set hash, input file hash.
  • Differential testing. Property-based tests (for example Hypothesis) generate random small projects; solver output must give zero referee violations; an intentionally broken allocation must be caught. The build fails otherwise.

7. Revisions: Rev A to Rev B

  1. Diff by tag (fallback: cable plus pair). Classes: unchanged, added, deleted, modified (type, cable, pair, group, segregation).
  2. Pin every unchanged signal to its Rev A slot. Deleted signals free their slots (they become new spare capacity).
  3. Place additions with an escalating search: wired spare pairs on the same cable (zero moves), free slots in the same kit, same lane's CIOCs, new baseplate in the lane's CIOC, new CIOC in the same cabinet, new cabinet.
  4. Modified signals. A changed IO type changes CHARM but may keep the slot; a changed group or cable may force a move. Resolve with the same escalation.
  5. Release radius. If pinned positions make the problem infeasible, release neighbours step by step (slots, baseplate, CIOC, cabinet) and re-solve with the moves penalty. Record the radius needed.
  6. Impact report. Added, deleted, moved, unchanged counts; list of moved signals with from, to and reason code ("cable CBL-105 grew from 12 to 24 pairs and needs 12 contiguous slots"); cabinets touched; ripple radius; stability score (share of unchanged signals still in the same slot; target 99% or higher for small revisions).

8. Reports

  • Allocation sheet in the customer's template (map columns with a template adapter file, keep styles).
  • Summary sheet: cabinets and CIOCs needed, fill % and spare per cabinet, per-group footprint, gap versus lower bound.
  • Rule-check report from the referee and the TQ log.
  • Revision impact workbook and board overlay.

Likely judge questions

Where is the AI?

In the parts that need language and judgement: mapping messy columns, turning plain-English requests into rules, writing customer queries, mining rules from past projects. Placement is a constraint problem and engineers need guarantees, so the solver places and a referee proves.

How do you guarantee zero violations?

The referee re-reads the output file and checks every enabled rule independently of the solver. It is tested against random projects and against deliberately broken allocations.

What if the rules cannot all be satisfied?

The static checker warns before solving, and for the allocation we raise TQs with the conflicting rule, the affected signals and options, instead of silently breaking a rule.

How optimal is the result?

We compare cabinets used with a capacity lower bound and report the gap. The first objective is fewer cabinets.

Does it scale?

10,000 signals is about 900 kits; we use a warm start, decomposition and time-limited CP-SAT. We benchmark up to 25,000.

How does a revision keep signals in place?

Unchanged signals are pinned, additions use spare pairs and nearby free slots first, and the search radius widens only if needed. The impact report shows the ripple radius.

Can users add a rule you did not foresee?

Yes, with existing rule types through the panel, or a new type as a small plug-in with its own check function that the referee automatically uses.

What if the template is different?

The output is produced through a mapping file, so a new template means a new mapping, not new code.

Is this specific to DeltaV?

Phase 1 is DeltaV. Capacities and mapping live in a hardware profile, so another DCS is a new profile and perhaps a rule plug-in.

Understand the problem

In plain words

A P&ID (piping and instrumentation diagram) is the engineering drawing of a process plant: tanks, pumps, heat exchangers, hundreds of pipes with bends, crossings and valves, and instruments attached everywhere. It represents the plant as built, so it is cluttered. The operators' screens in the control room need a simplified picture of the same process: only major equipment (tanks, vessels, pumps, exchangers) and the instruments listed in the IO list (the instruments the control system actually reads), connected in the right flow order, drawn with straight lines and no crossings. Today an engineer marks up each P&ID by hand, traces the flow and redraws it. Every drawing is different, so it is slow and error-prone.

What the PDF requires

  • Input: customer P&ID PDF and IO list Excel. Output: a simplified sketch as PDF, PPT or image showing major equipment and all IO-list instruments with their tags, connected in correct flow order with correct direction.
  • A tag-check report: IO-list tags found versus not found on the P&ID.
  • A good output is complete, accurate (same connections and flow direction), smart (duty and standby shown as parallel lines), readable (left to right, minimal bends, no crossovers) and generic (works on a P&ID it has never seen).
  • The tool must create the sketch itself; declare any third-party tools, APIs or models; sample data is for hackathon use only and must not be shared.
  • Example in the PDF: 18 instruments drawn, 14 in the IO list; duty and standby pumps (P-101A/B), each with a PT and FT, crossing; the sketch shows two parallel lines.

Our concept: Untangle Graph

1. Drawing becomes a graph first

Everything is built on a correct connectivity graph with flow direction. Layout is then a pure graph-drawing problem. We never "trace and copy lines".

2. Series-parallel reasoning

Duty and standby pumps are a parallel composition of identical branches. Detecting that structure lets the layout draw them as parallel rows, which solves the "pumps cross each other" case by construction.

3. Trace-back and confidence

Click a line in the sketch and the original path lights up on the P&ID. Low-confidence elements are flagged. Trust comes from showing the source.

How it works inside

1. Ingestion: three kinds of PDF

Always keep a rendered image for visual overlays and for any vision-model step. Remember the PDF says sample files are not to be shared; keep them local.

2. Symbols and tags

  • Instrument bubbles. Circles with text inside (and sometimes a horizontal bar). In vector input, find circles of the bubble size; in raster input use Hough circles. Read the text into a tag such as PT-101A.
  • Equipment. Large closed shapes with a label nearby. The label's letter prefix gives the type (T or V tank or vessel, P pump, E exchanger), so shape recognition only needs to find ports. This shortcut makes the system robust to symbol-style differences between customers.
  • Valves. Bow-tie symbols on lines; control valves have an actuator on top; check valves show direction. Most valves are not in the IO list and will be contracted away, but their direction cues feed the flow solver.
  • Tag normalisation. Uppercase, strip spaces and dashes, map common OCR confusions (O and 0, I and 1, S and 5), then fuzzy-match to the IO list under the ISA grammar. Record exact, normalised, fuzzy or not found, with distance and confidence.
  • Optional learning. Where a model helps (symbol classification of crops, reading difficult tags) use a vision-language model or a small detector. Declare it. Cross-check with rules so that no answer relies on the model alone.

3. Lines

  • Extract line segments and polylines (vector) or detected segments (raster). Merge collinear pieces.
  • Classify by stroke width and dash pattern: thick solid is a process line; thin dashed or dash-dot is a signal line. Learn thresholds per drawing from the histogram of widths.
  • Snap and split. Snap endpoints within a tolerance (for example 1.5 times the stroke width). Split lines at T-junctions. A crossing without a junction dot is not a connection; a crossing with a dot, or a T, is. Detect small filled dots.
  • Ports. Where a process line ends on an equipment boundary, create a port on that equipment.
  • Instrument attachment. A signal line from a bubble to a process line or equipment attaches the instrument there. A bubble placed directly on a line attaches at that point.

4. Graph and flow direction

5. Simplification

  1. Define the keep set: major equipment plus IO-list instruments found.
  2. Contract every other node (elbows, reducers, minor valves, non-IO instruments) by merging its two incident edges. Remove dead ends (vents, drains) unless they carry an IO instrument.
  3. Represent IO instruments as taps: attached to the nearest process edge or equipment, ordered by distance along the flow.
  4. Check invariants: every IO tag found is still present; connectivity between kept nodes equals the original (reachability preserved); no dangling edge.

6. Series-parallel structure

Reduce the simplified graph repeatedly: merge nodes in series, merge parallel edges, and compare parallel branches. If two branches have matching sequences of component types (pump with a PT and FT, each) and common endpoints, mark them as a duty and standby group (name suffixes A and B are a supporting hint). The result is an SP-tree: series nodes lay out left to right, parallel nodes lay out as stacked rows. Parts that are not series-parallel (recycles, bypasses) go through the general layered layout, with the recycle edge drawn as a return path above.

7. Layout

  • Layering. After removing cycles, assign layers by longest path or network simplex, so flow goes left to right.
  • Ordering. Within layers, order by the barycentre heuristic to reduce crossings; keep SP groups together as clusters.
  • Routing. Orthogonal edges with a bend budget; instruments placed as bubbles on or just above their line, in flow order; minimum spacing for readability. Use ELK (elkjs, layered algorithm with orthogonal routing) or Graphviz dot with orthogonal splines. Constrain parallel groups to align.
  • Render. SVG with a small symbol library (tank, vessel, pump, exchanger, valve, instrument bubble), tags under symbols, arrowheads. Export to PDF, PPTX shapes and PNG.

Understand the problem

In plain words

A control cabinet is a steel box packed with hundreds of parts (power supplies, breakers, terminals, controllers) joined by hundreds of wires. Technicians build it by hand from a drawing: every part in its place with a label, every wire on the right terminal with a printed sleeve (a ferrule) on each end. Before shipping, a QC inspector holds the drawing and checks every part, label, wire and ferrule by eye, at assembly, at power-on and at each QC stage, then fills a check sheet by hand. It is slow, tiring and easy to miss things. The task: AI that looks at a photo, compares it with the drawing and tells exactly what is wrong.

Our concept: Eagle Eye

1. The drawing is the query

With little labelled data, we do not train a detector for "cabinet parts". The drawing and the Excel lists tell us exactly which labels, parts and ferrule texts to look for, and where. Reading text is then a closed-vocabulary matching problem, which is far more accurate than open OCR.

2. Three-lane verdicts

PASS, FAIL and VERIFY. A FAIL needs strong evidence. When glare, blur or occlusion leave us unsure, the item appears with a "needs a human glance" flag instead of a risky FAIL. This is how "never a false alarm" is honoured without pretending to see what cannot be seen.

3. Checks are plug-ins; fixes are tracked

Each check is a small module registered by a YAML line. An issue ledger tracks each FAIL through fix, re-photo and closure with before and after images.

How it works inside

1. Compile expectations from the drawing and lists

  • Drawing parser. From the GA PDF, extract text with coordinates and shapes. Cluster shapes into device rectangles, attach the nearest label text, group devices into rails by clustering y coordinates, order each rail by x. Result: an Expected Layout Graph with nodes (device id, label, type, rail, position in rail) and relations (left of, above, adjacent to).
  • Excel lists. Wire list rows give from and to and colour; label list gives expected labels. Build an expected ferrule table, one entry per wire end, keyed by the ferrule grammar FROM-pin/TO-pin.
  • Checklist compiler. Parse the QC checklist rows and map each to one or more registered checks (keyword rules, optionally an LLM suggestion that the user confirms once and saves). Rows with no matching check are marked manual and shown as such.
  • If the drawing is a raster image, fall back to OCR and a vision-language model for layout.

2. Photo preparation

  • Detect the backplate (largest light or orange panel) from edges and contours; estimate four corners; rectify to a front-on view. If detection fails, let the user click four corners once.
  • Normalise exposure (CLAHE), detect glare (saturated blobs) and mark those regions as low-visibility so checks that depend on them go to VERIFY rather than FAIL.
  • Tile the HD image with overlap so labels and ferrules are read at sufficient pixel size (target at least 30 to 40 pixels of text height).

4. Reading labels and ferrules

  • Labels. Crop each label plate, upscale 2 to 3 times, deskew, run OCR. Decode against the set of expected labels with a confusion-aware edit distance (O and 0, I and 1, B and 8, S and 5, Z and 2, dash variants cost little). Accept a match if the normalised distance is small and the margin to the second-best candidate is large; otherwise label unreadable.
  • Ferrules. Small sleeves at wire ends beside terminals. Detect bright cylindrical objects at terminal entries; crop; try rotations (0, 90, 270 degrees); optional super-resolution; decode against the expected ferrule table with the grammar. Partial reads (only PS11-L) are matched to candidates and scored.
  • Wire colour. Segment the wire pixels near the ferrule, convert to LAB, correct white balance using neutral references (white labels, grey backplate), classify against colour prototypes; detect green and yellow stripes by two-hue clustering. Compare colour among wires of the same cabinet to reduce lighting effects.

6. The decision engine and the verify lane

For each check result compute evidence features (detector score, OCR margin, visibility, glare overlap, resolution)
p_fail = calibrated probability that the item is truly faulty (logistic or isotonic on planted-fault validation data)
if p_fail >= T_fail and visibility is adequate  -> FAIL (with proof)
elif p_fail <= T_pass and evidence is positive    -> PASS
else                                               -> VERIFY  ("needs a human glance"; shown with the snippet)
Choose T_fail on validation data as the lowest threshold that gives zero false FAILs on clean photos; report recall at that point.

Every item still appears in the sheet; VERIFY items carry a distinct tag. If the organisers insist on strict PASS or FAIL, map VERIFY to "FAIL (low confidence)" in the Excel but keep the flag.

7. The re-check loop and ledger

  1. Store each inspection: photos, detections, results, checklist state, timestamps in SQLite.
  2. For a new photo, register it to the previous one with SIFT or ORB features and RANSAC homography, or LoFTR, so issue locations transfer.
  3. Re-run only the failed checks (and a quick regression on previously passed ones to catch newly introduced faults).
  4. Close fixed issues; keep still-failing issues open; log new issues; keep history with before and after crops.
  5. Produce the re-check report: closed, open, new.

Typing every keystroke is not needed. Aggregate typing bursts (start, end, characters). Candidates are told exactly what is captured, in the onboarding.

2. Provenance: who wrote each line

  • Maintain the document as lines with tags: human, ai, ai-edited. When the candidate presses insert or pastes text that matches an AI code block (fuzzy match above about 0.8), tag the lines as ai. A later edit that changes more than about 20% of a line's characters turns it into ai-edited.
  • At the end compute: share of final lines by tag, AI lines removed, AI lines rewritten, and the largest unreviewed paste (inserted with no run or test within two minutes).
  • This feeds the AI Reliance Map: the final code coloured by provenance, a quick, honest picture.

3. Phases

Label each event with an intent: clarify requirements, plan approach, generate code, debug an error, explain code, test or review, refactor. Rules classify non-chat events (a test run is "verify"). A small LLM call classifies prompts, checked against rules. Then segment by change points into Understand, Plan, Build, Verify, Fix, Reflect. Render as the Session DNA ribbon: coloured segments on a time axis with markers.

Understand the problem

In plain words

Software ships faster than it can be tested. Manual testing is slow and repetitive, automated suites lag behind new features, and bug reports often arrive without clear steps to reproduce. Small teams often have no tester at all. Build an AI agent that tests a web application the way a careful tester would: explore it, decide what to test, run the tests in a browser, and report real bugs with evidence.

What the PDF requires

  • Given a web app address and a short description, the agent explores the app like a real user.
  • It generates test cases for the main user journeys and edge cases, and runs them in a browser.
  • It files clear bug reports: steps to reproduce, expected versus actual behaviour, screenshots.
  • It turns successful journeys into reusable automated tests the team can keep running.
  • Optional: several cooperating agents, for example an explorer, a tester and a reporter.
  • Outcomes: on a sample app with deliberately planted bugs, the agent finds and correctly reports a measurable share; generated tests run on their own and can be repeated; every report can be reproduced by a person following its steps.
  • Stages: Stage 1 the testing problem, agent design, target sample app, and how accuracy and coverage will be measured. Stage 2 one key journey (for example sign-up and login), a generated test and at least one evidence-backed bug report. Stage 3 several journeys, cooperating agents, results on a planted-bug benchmark, a simple findings dashboard.

Our concept: ScoutQA

1. Only reproducible bugs reach the report

Before filing, a verifier agent replays the steps three times in fresh browser contexts. A delta-debugging step shrinks the steps to the minimum. This enforces the PDF's "reproduced by a person following its steps" automatically and lifts precision.

2. A benchmark we built ourselves

BugBench: a sample shop app with 20 to 30 planted bugs in categories. We report recall, precision, reproduction rate, duplicates and cost per bug, and compare against a random clicker and an agent without the verifier.

3. Oracle zoo, not one opinion

Many cheap, independent signals decide if something is wrong, and an LLM only judges what code cannot. Every finding says which oracle fired.

How it works inside

1. Observation and state fingerprint

  • Each step observes: URL, title, accessibility tree (roles, names, states), list of interactive elements with stable ids, visible text summary, network log (requests, status, timings), console log, and optionally a screenshot. The accessibility tree is cheaper and more reliable for the model than raw HTML.
  • State fingerprint = hash of the normalised URL path, the sorted signatures of interactive elements, and key text. States with the same fingerprint are the same node, so loops are detected and coverage is measurable.

2. Exploration policy

  • Graph G of states and actions (click, type, select, navigate, submit). The agent keeps a frontier of unexplored actions.
  • Score each candidate action by novelty (leads to an unseen state), risk (forms, payments, authentication, data mutations), and goal relevance from the app description. An LLM chooses among the top candidates with a one-line reason; code enforces budgets (steps, time, tokens) and filters destructive actions (log out, delete account) unless a charter says so.
  • Generated inputs. Valid, boundary (empty, very long, maximum), invalid, unicode and emoji, whitespace, injection-style strings (for our own sample app and only where authorised).

6. The Codifier

  • Convert a successful journey (action list plus assertions) into a Playwright test (TypeScript or Python) using role-based locators (getByRole, getByLabel, test ids), page objects for repeated flows, explicit waits for conditions, not sleeps.

Our concept: ProofPass

3. The plan creates proof

6. Role match and gap analysis

  • Role profile. From a job description (LLM extracts required skills and levels) or a template (Backend developer, Data analyst, ML engineer, Frontend developer, DevOps engineer): required skills with weights and minimum levels.

  • Order gaps by marginal gain and prerequisite graph (for example HTTP before REST before authentication).

  • "Re-verify" re-runs the analysis; the passport shows what changed.

2. Turn loop

  1. The user message arrives (typed or transcribed).
  2. Assessor (asynchronous) tags observable behaviours: asked a clarifying question, gave a status update with ETA, escalated appropriately, proposed rollback, blamed someone, stayed silent too long. Each tag carries the turn id and the span of text.
  3. Director updates flags and meters, evaluates beat triggers, fires timed events, and chooses which character responds.
  4. Actor generates the reply from its persona, current emotion, knowledge list and the flags that unlocked facts. A checker verifies the reply does not mention facts the character should not know and does not break character.
  5. The state snapshot is stored for this turn (enabling rewind).

3. Fairness through seeded worlds

For assessment use, fix the random seed and the beat schedule so every candidate faces the same facts, characters and events. Actor wording may vary, but the hidden facts and triggers are identical. Practice mode may add randomness for variety. This is the difference between a practice toy and a fair evaluation.

Understand the problem

In plain words

New developers often spend weeks understanding an unfamiliar codebase. Much of the important knowledge lives only in senior engineers' heads and is lost when they move on, while written documentation is usually incomplete or out of date. Build an AI mentor that reads a code repository and helps a newcomer understand it quickly, with every answer grounded in the actual code.

What the PDF requires

  • An architecture overview: main parts of the system and how they connect.
  • Guided tours of key flows, for example "what happens when a user signs up".
  • Answers to "how" and "why" questions that link to the exact files and lines they are based on.
  • Suggested starter tasks that help a newcomer make a first contribution.
  • Optional: keep the generated documentation up to date as the code changes.
  • Outcomes: works on a real open-source repository; every answer cites the code it relies on so it can be checked; a small test with peers showing newcomers understand the codebase faster with the mentor.
  • Stage 1: the onboarding problem, target users, approach, how answers stay grounded. Stage 2: question answering with cited code and an architecture overview for one repository. Stage 3: guided tours, starter tasks, documentation that updates with code changes, results from a small user test.

Our concept: CodeSherpa

1. Verified grounding

Answers are built as claims with citations (path:Lstart-Lend@commit). A verifier reopens the lines and checks that they support the claim. Anything unsupported is removed. When the evidence is thin, the mentor says so and points to where to look.

2. History is the memory

Why was this written this way? The answer lives in commit messages, blame, issues and pull request discussion. We route "why" questions to history, which is exactly where the knowledge in senior engineers' heads leaks into the record.

3. Living docs and tribal knowledge

Docs carry code anchors and refresh only when anchored code changes. Questions the mentor cannot answer go to a maintainer; the reply is saved as a verified note tied to the code.

How it works inside

1. The code model

  • Symbols. Parse each file with tree-sitter into functions, classes, methods with name, signature, docstring, line range and parent. Start with Python and JavaScript or TypeScript; add more as time allows.
  • Imports and calls. Build an import graph. Resolve calls by name and import mapping to an approximate call graph; mark uncertain edges as "may call".
  • Entry points. Detect main, CLI commands (argparse, click), web routes (Flask and FastAPI decorators, Express handlers, Django URLs), background jobs, message consumers.
  • Tests. Map test functions to the modules they import or exercise.
  • Data model. Detect ORM classes or schema files.
  • History. Commit log with messages, authors, files; line-level blame; co-change graph (files that change together reveal hidden coupling); pull request and issue text if the GitHub API is available.

2. Index and retrieval

  • Chunks are symbols with a context header: repo | path | Class > method | lines | one-line summary. Summaries are generated once offline and stored.
  • Hybrid search: BM25 plus dense embeddings combined by reciprocal rank fusion, then a small cross-encoder reranker.
  • Graph expansion: add callers and callees (one or two hops) and co-changed files of the top hits.
  • Question router. Classify the question: where or what (locate), how (flow), why (history), how to (task), who (ownership), architecture. Each type uses a different retrieval plan:
TypePlan
Where or whatHybrid search over symbols; return top definitions with citations.
How (flow)Find the entry point by retrieval; traverse the call graph; narrate the path.
WhyRetrieve the code, then git log -L or blame for those lines; read commit messages, linked issues and PR text; answer from them with citations to commits.
How to (implement or change)Locate extension points, similar existing code, tests to update.
WhoCODEOWNERS and blame statistics.
ArchitectureUse the module graph and the overview.

3. Answering with proof

Answer JSON from the model:
{ "summary": "...",
  "claims": [ { "text": "Signup is handled by create_user() in users/service.py",
                "citations": [ {"path":"users/service.py","start":41,"end":78,"commit":"a3f9c1e"} ] }, ... ],
  "uncertainties": [ "I did not find where the welcome email is sent." ] }

Verifier, per claim:
  1. the path exists at that commit and the line range is valid
  2. identifiers named in the claim appear in the cited lines (lexical support)
  3. an entailment check: "do these lines support this sentence?" -> yes / partial / no (small model or LLM)
  yes     -> keep, show a green citation chip
  partial -> keep with a "partially supported" flag
  no      -> remove; try one more retrieval round; if still unsupported, report in "uncertainties"
Grounding score shown on each answer: verified claims / total claims   (abstain if below a threshold)

4. Architecture overview

  • Weighted graph of files or packages: import edges, call edges and co-change weights. Run community detection (Louvain) to find modules; name each with an LLM from its top symbols and README snippets; limit to 6 to 12 components.
  • Draw a layered diagram: entry points, services or controllers, domain logic, data layer, external dependencies. Make each box clickable to a summary with key files, key flows, owners, and a "start here" reading order ranked by centrality.
  • Overlay hot spots (high change frequency and complexity) and dark corners (little test coverage or documentation).

5. Guided tours

  1. Pick a flow, such as sign-up, the main request lifecycle, data model, background jobs, or build and test.
  2. Find the entry point and traverse the call graph with limited depth. Prune plumbing (logging, getters, small utilities) using centrality and an "interestingness" score so each tour has 6 to 10 steps.
  3. For each step show the code with highlighted lines, a short explanation with citations, and a mini path diagram.
  4. Add predict-then-reveal mini-questions ("what do you expect happens next?") and a final quiz.
  5. Pre-generate tours for the top flows; allow custom tours from any question.

6. Starter tasks

SourceWhat is mined
IssuesLabels like good first issue and help wanted; clear reproduction steps.
CodeTODO and FIXME with blame age; skipped or xfail tests; missing docstrings in public APIs.

Score tasks by blast radius (reverse-dependency count), size and complexity of the area, test availability, and clarity. The output is a task card: why it matters, where (files and lines), reading list in order, steps, how to verify (commands and tests), pitfalls from history, who to ask (CODEOWNERS or top blame authors), estimated time, and the PR checklist from the contributing guide. A "first PR coach" can review the newcomer's diff against repository conventions.

7. Living documentation

  • Documentation is a set of sections (architecture, flows, glossary, FAQ). Each section stores anchors: symbol ids, file paths and content hashes.
  • On push or pull request, compute which anchors changed. Mark dependent sections stale and regenerate only those, citing the new code, then open a pull request with the doc diff.
  • A CI check can warn when code changes without matching doc updates, and a freshness badge shows the share of sections up to date.
  • The glossary is mined from identifiers and README terms.

8. Tribal knowledge capture

When the mentor abstains or the user rates an answer unhelpful, offer "ask a maintainer". The maintainer's reply is stored as a note anchored to the relevant code with a "maintainer-verified" badge, and used in future answers. If the anchor changes, the note is flagged for review.

9. Learning path and quizzes

Generate a reading path by role (backend, frontend, DevOps). Track progress. Short quizzes after tours check understanding with questions whose answers can be found in the code.
