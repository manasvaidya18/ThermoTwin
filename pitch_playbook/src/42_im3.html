Understand the problem

In plain words

Resumes list skills but rarely prove them. A student's real abilities are scattered across code repositories, project reports, portfolios and certificates. Recruiters cannot check all of that quickly, and learners often do not know which skills they lack for the role they want. Build an AI system that turns real work into a verified skill profile, with each skill backed by evidence and linked to a path for growth.

What the PDF requires

  • Analyse a person's work: code repositories, project documents, a portfolio or certificates.
  • Produce a skill profile in which every skill and level links to cited evidence (a project, a file or a piece of work).
  • Compare the profile with a target role and show matches and gaps; generate a personalised learning plan to close the gaps.
  • Offer a shareable "skill passport" view a recruiter can read in under a minute.
  • Guard against invented claims: a skill without evidence must never appear as verified.
  • Outcomes: passports for a few sample users from public or sample data; every claimed skill traceable to its evidence; a clear explanation of how well a person matches a role, and why.
  • Stage 1 must name the skill framework, data sources, how evidence links to each skill, and passport mock-ups. Stage 2: a passport from one public code repository and a resume with every skill linked to evidence. Stage 3: multiple data sources, role matching, learning plans, a recruiter view, and checks that prevent unsupported claims.
  • Use public, sample or synthetic data; do not use real people's personal information without consent.

Our concept: ProofPass

1. Evidence first, language second

Code extracts evidence deterministically (dependencies, code structure, tests, CI, git history). The language model only organises and phrases, and may cite nothing but evidence ids that a checker verifies. Unsupported sentences are deleted, not softened.

2. Claim versus proof

Resume claims become a ledger: Verified, Weak evidence, Claimed only, Contradicted. Claimed-only skills never count toward the score. The planted-lie test proves it: fake skills in a resume must stay unverified.

3. The plan creates proof

Each learning-plan step is a small project whose output is analysed again. A gap can become Verified, so the loop closes. A short quiz built from the person's own code checks they understand what they submitted.

Why we win

It is built on a promise that is easy to test: nothing unproven is shown as verified. A planted-lie experiment and a 100% traceability number make the claim real. The quiz built from the candidate's own repo is a memorable anti-gaming feature.

Why we might lose

Crowded. Many teams will produce "resume plus GitHub into a skill chart". Differentiate through evidence rigour, the lie test and the closed learning loop; do not rely on visual polish alone.

How it works inside

1. Skill framework

Stage 1 requires naming the framework. Proposal: a compact internal ontology of about 120 to 200 software skills in three levels (domain, skill, sub-skill), each mapped where possible to identifiers in open frameworks such as ESCO or O*NET so the passport can speak a standard language. Keep it small enough to define a recipe for each skill. Levels use a five-point scale with behavioural definitions:

LevelNameMeaningEvidence needed
L0NoneNo trace.None
L1AwareUsed in a basic way (a tutorial-level artefact).One artefact
L2WorkingBuilt something that runs using the skill.At least two independent artefact types
L3ProficientApplied it with good practice (tests, structure, error handling) across more than one project.Several artefacts with quality signals
L4AdvancedDesign-level decisions, performance or scale concerns, review of others' work.Deep, varied, recent evidence

2. Evidence extraction

SourceWhat is extracted
Dependency manifestsFrameworks and libraries used (requirements, pyproject, package.json, pom, go.mod).
Source code (AST)Language features (async, typing coverage, decorators, generators), module structure, error handling, API routes, database models, ML training and evaluation scripts, data pipeline stages.
Tests and CITest files and counts, test-to-code ratio, CI workflows that run tests or deploy, lint and type-check configuration.
Infrastructure filesDockerfile (multi-stage?), compose, Kubernetes manifests, Terraform.

DocumentationREADME structure, architecture notes, setup instructions that actually match the project.
Resume and reportsClaims (skill, claimed level, context), results claimed ("92% accuracy") to cross-check with scripts and logs.
CertificatesIssuer and id; verified only if a public verification link or id check succeeds, otherwise "self-declared".

Each evidence item is stored as {id, type, source (repo, path, line range, commit, URL), snippet hash, strength, timestamp}. Authorship share comes from git blame by author identity (the user confirms their emails). Vendored and generated code is excluded. Forks and template boilerplate are down-weighted using the fork flag and file-hash comparison against common templates and between the candidate's own repos (MinHash).

5. Language that must cite

  • The model produces JSON: a list of statements, each with skill, level, text and evidence_ids[].
  • The verifier checks that each id exists; that the cited file and line range exist at the cited commit; that identifiers or numbers in the statement appear in the evidence; that the statement's level does not exceed the evidence-derived level. Failures: regenerate once with a stricter prompt, otherwise delete the statement. Fail-closed.
  • Numeric claims from reports ("accuracy 92%") must match a logged value or the item stays unverified.

6. Role match and gap analysis

  • Role profile. From a job description (LLM extracts required skills and levels) or a template (Backend developer, Data analyst, ML engineer, Frontend developer, DevOps engineer): required skills with weights and minimum levels.
  • Match score = sum over skills of weight × min(1, verified level ÷ required level), divided by total weight. Unverified skills contribute zero, which makes the number conservative. Show a "potential if claims were verified" figure separately.
  • Explanation. A matrix of required versus achieved, top three blockers, and marginal gain: "adding SQL L2 raises your match from 64% to 78%".

7. Learning plan that produces evidence

  • Order gaps by marginal gain and prerequisite graph (for example HTTP before REST before authentication).
  • Each step: what to learn (from a curated resource list, so no invented links), estimated hours, and a proof task: a small project spec with acceptance checks the analyser can verify.
  • Weekly plan within the person's available hours.
  • "Re-verify" re-runs the analysis; the passport shows what changed.

8. Understanding quiz from the person's own code

Pick two functions from the person's strongest evidence and ask a short question about each ("what does this function return for an empty list?", "why is this index created?"). The answer key comes from running the code or from the code itself. It deters showing off someone else's repository and adds a trust signal. Keep it optional and short.

9. Passport and sharing

  • One-minute recruiter view. Name, target role, match score, a trust bar ("17 of 22 shown skills verified"), the three strongest proofs, the top gaps, and red flags (single-commit dumps, contradicted claims).
  • Evidence drawer. Click any skill: evidence list with file, line, snippet, commit link.
  • Tamper evidence. Export the passport as JSON, hash the evidence snapshot, sign it (Ed25519) and show a QR code to a verification page. A changed passport fails verification.
  • Interview helper. Suggested interview questions drawn from the person's strongest and weakest evidence.
  • Placement-cell cohort view. Aggregate skill coverage versus role demand across students; identify who needs support.

Screens and flows

  • Connect. GitHub username or repo URLs, resume upload, certificate links, consent checkbox.
  • Analysis progress. Evidence items appearing live, counts by type.
  • Passport. Skill grid with level and status chips; trust bar; role match gauge; evidence chips on every skill.
  • Evidence drawer. File, line range, snippet, commit, why it counts.
  • Claims ledger. Table of resume claims with status.
  • Role match. Choose a role or paste a job description; matrix, blockers, marginal gains.
  • Learning plan. Weekly list with proof tasks; re-verify button.
  • Recruiter view. One page; share link; QR.
  • Cohort. Heat-map of skills versus roles.

Data and evaluation

  • Samples. Eight to ten passports: repos of consenting teammates, public open-source maintainers' repos (with public data only), and synthetic personas. Never use real people's personal data without consent.
  • Planted-lie test. Add false claims to resumes. Target: false-verified rate 0.
  • Traceability. Every displayed skill and statement links to at least one existing evidence item. Target: 100%.
  • Claim-level accuracy. Hand-label about 100 claims; measure precision and recall of Verified status.
  • Level agreement. Three human reviewers assign levels on a subset; report agreement with ours (weighted kappa or Spearman).
  • Recruiter reading test. Five peers answer five questions about a candidate from the one-page view; target under 60 seconds with 80% correct.

Pitch kit

30-second pitch

A resume says "Docker, SQL, REST". Who checks? ProofPass reads a student's real work, repositories and projects, and builds a skill passport where every skill links to evidence you can open. Anything without proof is shown as unproven, never verified. It matches the profile to a target role, explains the gaps, and gives a learning plan whose projects create new proof. A recruiter reads it in a minute and can verify it has not been altered.

5-minute demo script

  1. 0:00 Problem. A resume with ten skills; "which are real?"
  2. 0:40 Connect. GitHub repos plus the resume. Evidence items stream in.
  3. 1:30 Passport. Verified skills with chips; open one evidence drawer: file, lines, commit.
  4. 2:15 The lie test. The resume claimed Kubernetes and Rust; the ledger shows Claimed only, with no credit.
  5. 3:00 Role match. Choose "Backend developer": 71%; blockers and marginal gains.
  6. 3:40 Plan. Proof task for SQL; re-verify shows a change.
  7. 4:15 Recruiter view and QR. One-minute page; scan; "valid".
  8. 4:50 Close.

Likely judge questions

How do you stop the AI from inventing skills?

It can only cite evidence ids; a verifier checks each citation against the repository and deletes anything unsupported. We also run a planted-lie test.

How can you tell someone wrote the code themselves?

Authorship share from git blame, history shape, template and duplicate detection, and an optional quiz about their own code. We state it is strong evidence, not proof.

What skill framework did you use?

A compact internal ontology mapped to open frameworks such as ESCO and O*NET, with explicit level definitions and evidence recipes.

Is it biased towards GitHub users?

Yes, as a limit. Reports, certificates and portfolios are also sources, and the plan is built to create new evidence.

How is the role match computed?

Weighted coverage of required skills by verified level, conservative by construction, with a separate "potential" figure and a marginal-gain explanation.

What about privacy?

Public or consented data only, local analysis possible, and the person controls what is shared.
